# AGENTS.md — KALFA Agent Console (native Android)

Call-center agent app for kalfa.me (Hebrew RSVP SaaS): agents supervise AI voice-RSVP calls, take inbound calls, run outbound campaigns, and watch a realtime dashboard.

**This app is a separate product from `kalfa.me/beta` (the Next.js web app).** It talks to that server over the HTTP contract in §"API contract" and reads the same Supabase project through PostgREST/Realtime with the agent's own JWT. It does not share code, a repo, or a deploy pipeline with `beta/`. Where a decision genuinely depends on how the server works, this file says so and names the boundary — it does not restate the server's implementation.

## Hard rules

1. **Hebrew-first RTL.** All user-facing strings in Hebrew. `LayoutDirection.Rtl` everywhere; paddings/margins use `start`/`end` only — never `left`/`right`. Phone numbers, digits, times, and dates render LTR inside RTL text.
2. **Design system: Bento Grid.** Keep the established Bento Grid layout language — rounded cards on a clean canvas, flat design, no gradients. Brand: primary `#6C4CF1`, secondary `#6366F1`.
3. **Supabase is the ONLY backend.** supabase-kt (auth-kt, postgrest-kt, realtime-kt) version 3.x with Ktor 3.x. Package is `io.github.jan.supabase.auth` (not gotrue). No Firebase Auth / Firestore / any Firebase dependency — the single exception is `firebase-messaging` (FCM push only). Secrets never in code: `SUPABASE_URL` / `SUPABASE_ANON_KEY` reach BuildConfig via the secrets-gradle-plugin from the git-ignored `.env` file (see `.env.example`).
4. **Telephony lives behind `CallEngine` / `CallSession` / `AgentPresence`.** Do NOT rename or remove these interfaces — every swap happens behind them.
   - **The Voximplant SDK line is v3** (`com.voximplant:android-sdk-bom` + `-core` + `-calls`, version `3.2.0`), NOT the legacy monolithic v2. This app is Compose + coroutines end-to-end, so v3 (modular, coroutine-friendly, actively maintained) is the right line — the earlier "v2 GA, v3 still Beta" call this file used to make is stale; v3 left beta in 2026-07 and this app has been building against it since.
   - **A real v3 login + call-session layer already exists**, under `telephony/vox/`: `VoxClientManager` (connect/one-time-key login, MAU-safe — never logs in speculatively), `VoxSdkAuthClient` (talks to `POST /api/agents/sdk-auth`), `VoxCallSession` (wraps a real `Call`: mute/hold/DTMF/hangup, state mapping), `VoxAudioController` (device selection), plus `telephony/CallForegroundService` (microphone-type FGS) and `telephony/CallAudioPermissions` (RECORD_AUDIO + POST_NOTIFICATIONS, already requested on the live-calls screen).
   - **None of that is wired into `CallEngine` yet.** `SupabaseCallEngineImpl.startOutboundCall` / `.monitorCall` / `.takeoverCall` all `throw UnsupportedOperationException` on purpose (`data/SupabaseImplementations.kt:892-906`) — they used to fabricate a `MockCallSession`, which was the worse, dishonest option, and were changed to fail loudly instead. `VoxClientManager` is constructed in `di/DependencyContainer.kt:103` but `ensureLoggedIn` is never called from anywhere. Wiring these together — instantiate `VoxClientManager`/`VoxCallSession` from the real `CallEngine`, answer the incoming SDK call `VoxClientManager.onIncomingCall` delivers, start/stop `CallForegroundService` around the leg — **is the concrete Voximplant work still open in this repo.** See "Known state" below before starting it.
   - Self-managed Telecom (`ConsoleConnectionService`) is **not built** — no such class exists yet, and the manifest entry for it is commented out with a `TODO(voximplant-phase)`. `MANAGE_OWN_CALLS` / `FOREGROUND_SERVICE_PHONE_CALL` are deliberately NOT declared until it lands (declaring them with nothing behind them is a Play-review risk, not a shortcut).
   - The mock implementations stay in the tree as the offline/unconfigured fallback (DEBUG builds only — `di/DependencyContainer.kt`'s `mockOrFailClosed` refuses them in `release`); they are not deleted.
5. **Architecture:** Kotlin + Jetpack Compose (Material 3), single-activity, sealed classes for call/campaign state, one immutable `UiState` per ViewModel exposed as `StateFlow`. Every screen has a `@Preview` with fake data. DI: `di/DependencyContainer` (manual service locator) — Hilt is still approved but not yet migrated; the fake→real `CallEngine` swap that was meant to trigger it is now the telephony-wiring step above, not yet done. Migrate incrementally; do not rewrite working screens to chase it.
6. **Allowed libraries:** Compose BOM, Hilt, supabase-kt, Ktor client (okhttp engine), kotlinx-serialization, Coil, firebase-messaging, `com.voximplant:android-sdk-bom`/`-core`/`-calls` (v3, **not** the legacy `voximplant-sdk` v2 artifact), accompanist-permissions. Anything else — ask first.
7. **Source of truth, and its limits.** This file is the contract, but it is NOT automatically current: the production schema and the server routes change in the `kalfa.me/beta` repo, not here. Where this file and the live database — or the server's own contract doc, `beta/docs/voice-agent/app-integration-reference.md` — disagree, **the server side wins**, and fix this file in the same change. Never invent an API path or a column name; if you cannot verify one, ask.
8. **Identity:** base package and applicationId are `me.kalfa.agentconsole` — never `com.example` or AI-Studio-generated ids (Google Play rejects them). Leftover template tests still under `com.example` (`app/src/test/java/com/example/*`, `app/src/androidTest/java/com/example/*`) may be deleted or rewritten.
9. **KSP versioning:** KSP now uses standalone versions (2.3.x line, decoupled from Kotlin). Do not force the legacy `<kotlin>-<ksp>` format.
10. **Functional code first.** No marketing READMEs or comments-as-docs. **Exception, explicitly approved:** the telephony layer (auth flow, Telecom/ConnectionService lifecycle, monitor/takeover media routing) MUST carry comments explaining *why* — it is the one part of this app whose failure modes are invisible in the code and expensive in production. **Scope clarified 2026-08-14:** this rule governs inline code comments (don't pad a function with a comment that just restates the line beneath it) — it does not mean the top-level `README.md` should stay a thin stub. A real, evidence-based README is documentation a reader needs before they can work in this repo at all, which is a different thing from a comment restating obvious code; the rule was being read as covering both, and a genuinely useful README had not been written as a result. Keep the README substantive; keep code comments lean except where §4 requires the why.

## Push wake-up — resolved architecture, and a caveat that matters more than the architecture

**The reason this app exists:** the browser PWA only receives calls while a tab is open and its 60s heartbeat keeps flowing — a closed laptop silently drops out of the routing pool (`agent_status.updated_at` ages past the 90s freshness window server-side; see `beta`'s `AGENT_STATUS_FRESHNESS_MS` / `findRoutableAgents`). A foreground service fixes "stays reachable while the app is running." It does **not** fix "gets woken when the app isn't running" — that needs push.

### Decided 2026-08-14: Voximplant delivers the push itself — no backend work in `beta`

Two candidate architectures were considered. Verified against live Voximplant docs (`references.androidsdk3.*`, `guides.sdk.android-push`), quoted verbatim: *"Call push notifications are sent automatically. Call the `callUser` method in the VoxEngine scenario and a push notification is automatically sent to the app."* Corroborated by a platform-emitted `Call.PushSent` event with a `push_results[]` array in session logs — the platform reporting on its own send.

**So: no `firebase-admin`, no new Supabase table, no new API route, no new secret, no backend send path in `beta`.** A self-hosted FCM sender (a `console_agent_push_tokens` table + `POST /api/agents/push-token` + a `src/lib/push/fcm.ts` send path parallel to the existing web-push stack) was fully specified in an earlier pass of this document and then ruled out for exactly this reason — it would have duplicated infrastructure Voximplant already provides on the one path where the platform is the natural owner. Not reproducing the detail here on purpose; if this decision needs re-deriving, start from the Voximplant guide quote above, not from scratch.

**What beta's existing push stack (`src/lib/push/{web-push,types,browser}.ts`, `push_subscriptions` table) still is:** Web Push (VAPID) for the browser PWA only. It was never a candidate for the native path — the table shape (`endpoint`/`p256dh_key`/`auth_key`) is Browser Push API-specific and has no equivalent for a Voximplant-delivered native push. Nothing about it changes; it just isn't part of this story.

### What IS needed — entirely client-side, in this repo

- **One-time ops action, not code:** upload the Firebase service-account JSON to the Voximplant control panel (Applications → `kalfa-rsvp` → Push Certificates → GOOGLE). Without this, `callUser` sends no push regardless of anything the app does.
- **Scenario side, one line:** `require(Modules.PushService);` added to `ConsoleInbound.voxengine.js` — no change to any `callUser` call site. Server/ops work, out of this repo, but trivial compared to the backend spec that was ruled out.
- **App side (the actual work here):**
  - Standard Firebase client registration: `google-services.json`, the Google Services Gradle plugin — this is the sink for the `firebase-messaging` dependency that has sat unused since the project was scaffolded. Note the plugin isn't just missing, it was **deliberately removed**: commit `337823b` stripped it from the AI Studio export precisely because there was no JSON yet ("google-services plugin (no JSON yet)"). Re-adding it is a real, if small, step — not just dropping a file in.
  - A `FirebaseMessagingService` subclass forwarding `onMessageReceived` into `Client.handlePushNotification(map)`.
  - `registerForPushNotifications(PushConfig(token))` called after a successful SDK login.
  - `VICalls.setIncomingCallListener` (already present in `VoxClientManager` — `onIncomingCall`) is what fires once the platform delivers the woken-up incoming call.
  - **Persisted-token silent login** (`loginWithAccessToken`/`refreshToken`), not the one-time-key flow, for the wake path specifically: a push-woken app has no human present to type a password, and Voximplant's own guide discourages storing one. The one-time-key flow in "Telephony integration spec" §1 is still correct for an interactive, foreground login — this is a second, separate login path needed only for the wake case.

### The caveat that matters more than the architecture: push does not fix the 13.8 incident

**Verified directly** (`beta/src/app/api/voximplant/console/route-inbound/route.ts:171,242` and `src/lib/data/console-calls.ts`'s `findRoutableAgentVoxUsernames`): `ConsoleInbound` only rings usernames the SERVER hands it as `ring_order`, and `ring_order` is built from `findRoutableAgentVoxUsernames()` — the SAME `status='ready'` + fresh-heartbeat gate as everywhere else in this document. An agent with a stale heartbeat is excluded from `ring_order` **before `callUser` is ever attempted** — which is exactly what happened on 2026-08-13 (`status='ready'`, heartbeat 661 minutes stale, every call answered "no agent available"). No `callUser` attempt means **no push would ever have been sent**, push infrastructure notwithstanding.

**Push solves the telephony layer** (a `callUser` attempt reaching a backgrounded or killed app). **It does nothing for the routability layer** (an agent already excluded before `callUser` is tried).

**Update, 2026-08-14 — the server half has since been decided and shipped** (`beta` commit `8af24ab`, deployed). The resolution was NOT to loosen the freshness gate. Instead, `POST /api/voximplant/console/route-inbound-retry` — the one-shot RETRY wave the scenario fires after the primary ring is exhausted — now returns two audiences in order: heartbeat-fresh agents first (awake, answer immediately), then agents whose `console_agent_shift` row is active and fresh, **without** the heartbeat requirement. Ringing that second group is precisely what makes Voximplant push their device: no `callUser`, no push.

What that changes for this repo:

- **The primary ring is unchanged.** A stale-heartbeat agent is still excluded from the first pass, exactly as on 2026-08-13. This adds a second chance after the first pass fails; it does not make that incident impossible, and nobody should describe it that way.
- **The server side now needs nothing further.** What remains is entirely in this repo (FCM registration, `FirebaseMessagingService`, silent login), plus the one-time control-panel upload and the one-line `require(Modules.PushService);` in the scenario — both ops, not app code.
- **This app must call `POST /api/agents/shift` for any of it to work.** It currently does not (see the API-contract section). With no `console_agent_shift` row, the retry wave will never include this agent and no push will ever be sent, no matter how correctly the FCM side is wired. Treat wiring `/api/agents/shift` as part of the push-wake work, not an optional extra.
- **The cold-start budget is real and unmeasured.** The retry wave rings with `RING_RETRY_WINDOW_MS` (15s) — tighter than the primary `RING_PER_AGENT_MS` (20s). FCM delivery, connect, silent login, `onIncomingCall` and answer all have to fit inside it. No documented SLA covers this; it needs a live-device timing test before anyone claims the path works.

### Two more things worth knowing before this gets built

- **MAU is not the constraint it was treated as earlier in this document.** Multiple devices logged in under one credential count as ONE MAU, and a push-triggered reconnect + silent login on the SAME credential is another login on that same credential — it does not multiply per wake-up. The underlying discipline ("don't log in speculatively when there's nothing to do yet") is still good practice for the interactive one-time-key path, but MAU exhaustion specifically is not a realistic risk for the push-wake path.
- **Unmeasured timing risk, flag before trusting this in the primary ring:** a cold wake — FCM delivery → SDK connect → silent login → `onIncomingCall` fires → app answers — has to complete inside `RING_PER_AGENT_MS`, **verified as `20000` (20s)** in `beta/voxfiles/scenarios/src/ConsoleInbound.voxengine.js:84`. Voximplant's docs promise the push is sent "without delay" but give no number for end-to-end wake latency on a real device. This needs a live-device timing test — cold app state, real network, real OEM — before push-wake is trusted to answer in the primary ring rather than being scoped to a retry wave. Also account for Doze/OEM battery managers, which can swallow a push the platform's own `Call.PushSent` log reports as delivered — "the platform says it sent it" and "the device received it in time" are different claims.

### Done 2026-08-14: the app-side work, and what it does NOT yet close

Built: `telephony/vox/VoxFirebaseMessagingService` (registered in the manifest; `onMessageReceived` runs the app-side steps of the documented six-step sequence — login/connect if necessary → `Client.handlePushNotification` → re-register the token — **blocking**, under a 9s internal timeout, because `FirebaseMessagingService` is a `Service`, not a `BroadcastReceiver`: there is no `goAsync()`, and the framework already holds the process up while `onMessageReceived` runs). `VoxClientManager.ensureLoggedIn` now tries `loginWithAccessToken` → `refreshToken`+retry → the original interactive one-time-key flow, in that order, persisting whatever `AuthParams` the SDK returns after each success (`telephony/vox/VoxTokenStore`, plain DataStore Preferences — see its kdoc for why not `androidx.security`: this app's own supabase-kt session manager already stores a strictly more powerful credential, the Supabase refresh token, in plain app-private SharedPreferences). `ConsoleViewModel.setAgentStatus(READY)` now calls `POST /api/agents/shift {active:true}` and triggers the Voximplant login + push-token registration; `logout()` withdraws shift, unregisters the push token, and clears the persisted session.

**Still open, and load-bearing:**
- `VoxClientManager.onIncomingCall` has no listener assigned anywhere — that lands with the "Voximplant v3 SDK wired into `CallEngine`" phase (still **OPEN**, see the phase table). Until then, a push-woken app gets the SDK logged in and registered for push, but a delivered incoming call has nowhere to go and is dropped. Do not describe push wake-up as answering a call end to end until that phase closes.
- The `loginWithAccessToken`/`refreshToken` parameter order (`fullUsername, token, callback`) is inferred from this SDK's own internal consistency (byte-verified via `javap` against every other `Client.login*` overload, all `(String, String, Callback)`) — it is **not** confirmed against a rendered docs page. `voximplant.com/docs`'s search-driven doc pages returned an empty client-side shell to automated fetches during this change (the JS-rendered content never loaded). Re-verify if `loginWithAccessToken`/`refreshToken` ever fail at the SDK boundary with an argument-shaped error.
- The `AuthParams.accessTokenTimeExpired`/`refreshTokenTimeExpired` unit (seconds-duration vs. absolute epoch-seconds) is likewise unconfirmed for Android v3 specifically; `VoxTokenStore`'s `resolveExpiryMs` disambiguates by magnitude (implausible-as-a-duration ⇒ treat as absolute) rather than guessing — see its kdoc.
- The cold-start timing risk two bullets up is **still unmeasured** — this change does not resolve it, it only makes the path exist to measure. Three distinct paths have different budgets: the happy path (stored access token still valid: one `loginWithAccessToken` round trip) most plausibly fits inside `RING_RETRY_WINDOW_MS`; the expired-access-token path (adds a `refreshToken` round trip + a second `loginWithAccessToken`) is tighter; the tokens-gone interactive fallback (adds `requestOneTimeKey` + a round trip to `beta.kalfa.me` + login) adds the most latency and is reached precisely when a device has been idle long enough for both tokens to lapse — plausibly does NOT fit. A live-device test needs to measure all three, not just report one verdict.
- `MobileServices` on `ConnectOptions` (`Google` / `Huawei`, byte-verified in `android-sdk-core` 3.2.0) is the real v3 replacement for the old `ClientConfig.useHmsForPushNotifications` this document used to call unverified — Huawei push is answerable, just not implemented (nothing in this repo targets Huawei devices today).

## Telephony integration spec (for finishing the wiring)

### 1. Authentication — mostly done, verify against this before changing it

The real flow, as implemented in `telephony/vox/VoxClientManager.kt` + `VoxSdkAuthClient.kt`:

```
Client.connect(ConnectOptions(VoxConfig.node))
  → Client.requestOneTimeKey(fullUsername)                     // full username, not short
  → POST https://beta.kalfa.me/api/agents/sdk-auth {one_time_key}  → {hash}
  → Client.loginWithOneTimeKey(fullUsername, hash)
```

- The hash is computed **server-side only** (`beta`'s `src/lib/data/console-sdk-auth.ts`, `computeOneTimeKeyHash`): `MD5(oneTimeKey + "|" + MD5(shortUsername + ":voximplant.com:" + password))`. The Vox password never reaches the APK.
- `VoxConfig.fullUsername` builds `${voxUsername}@kalfa-rsvp.kalfarsvp.voximplant.com` in exactly one place (`telephony/vox/VoxTelephony.kt`) — pinned by `VoxConfigTest`.
- **Node: resolved, `Node.Node1`.** `VoxConfig.node` used to say `Node.Node2`, "confirmed" from the account's Management API endpoint hostname (`api-node2.voximplant.com`) — that reasoning was wrong, not just weak: the Management API (`beta/src/lib/voximplant/core.ts`) is a different service from the SDK's realtime connection, and its base URL isn't even node-specific (`https://api.voximplant.com/platform_api`, generic). The actual evidence is `beta/src/lib/voximplant/core.ts`'s `MEASURED_CONNECTION_NODE`: a real browser one-time-key login **succeeded on `NODE_1` and no other node tried**, 2026-08-12 — an empirical login against this exact account beats a hostname inference. Fixed in code (`VoxTelephony.kt`) to `Node.Node1`, with the corrected provenance in a comment there. **If `Client.connect()` ever fails, re-check this constant first** — a wrong node fails silently at `connect()`, not `login()`, so it presents as a network problem, not an auth one.
- **MAU discipline still applies and is not yet enforced by any call site** (there isn't one yet): call `ensureLoggedIn` only when a real leg must be handled — never on app launch, never on "Ready" — each login counts against the 1,000/month quota and can fail with `LoginMauAccessDeniedError`.
- `console_me.vox_username` (nullable) is already threaded into the domain layer (`ConsoleMe.voxUsername`, populated in `ConsoleViewModel.loadIdentity`) — read it from there rather than re-fetching.

### 2. Audio & Hardware (v3 SDK)

### 3. Android Telecom & Permissions

### 4. Live Monitor & Takeover (server-verified topology — do not reinvent)

This section previously described a pattern (`Conference.add(EndpointParameters)` taking an `AgentsClient`) that does not compile against the real typings and was corrected on the server side after a live-docs check. The verified topology, 1:1 from Voximplant's official supervisor guide (`beta/docs/voice-agent/monitor-scenario-topology.md`):

- A `Call` receives only **one** audio stream — a new `sendMediaTo` source replaces the previous one. A leg that must hear two sources (guest + AI) needs a mixer: `VoxEngine.createConference()`, **not** `Conference.add()` (which needs a video-conference rule flag and does not accept an `AgentsClient` at all).
- `monitor` = Supervision mode: `guest.sendMediaTo(conf); agent.sendMediaTo(conf); conf.sendMediaTo(human)` — the human leg only receives.
- `takeover` = full Conference mode: all three legs `sendMediaBetween`/`sendMediaTo` the mixer both ways.
- This is **entirely server/VoxEngine-scenario work** (`RSVPAgent.voxengine.js`), gated behind `app_settings.monitor_enabled` and blocked on live-call verification — not something to implement from the app side. The app's job once the server flag is on: call `POST /api/calls/{id}/monitor` `{mode}`, get back `202 {leg_id, request_id}`, watch `human_agent_call_legs`/Realtime for `dialing → ringing → connected`, and answer the incoming SDK call that arrives via `VoxClientManager.onIncomingCall` — wrapping it in a `VoxCallSession` with `connectedState = MONITORED` or `TAKEN_OVER` (both already exist as domain states, see `CallSession`/`CallState`).
- **Open owner decision, not resolved yet:** whether `takeover` should mean a 3-way conference (agent+human+guest, AI never disconnected) or a full swap (AI closed via the existing `close_agent` command, guest left alone with the human). The server doc's default is the 3-way conference; confirm before building UI copy that promises one or the other.

## Data model (REAL production schema — kalfa-event-magic project; names are fixed)

Realtime tables (postgresChangeFlow; always start collecting BEFORE channel.subscribe()):
- `agent_status(agent_id, status: ready|not_ready|dnd|in_call, updated_at)` — agent updates own row only. `in_call` is server-managed; the app must never write it.
- `console_call_feed(call_attempt_id, event_id, campaign_id, direction, kind, status, handled_by: ai|agent, agent_id, rsvp_digit, finish_reason, call_duration_sec, callback_iso, created_at, updated_at, takeover_claimed_at, takeover_request_id, participation_state)` — trigger-fed from `call_attempts`, deliberately PII-free (no phone/transcript/recording). Live `status` values: `in_progress|completed|no_answer|cancelled|no_response`.
  - **The last three columns are the takeover coordination fields and the app does not read them yet** (`DbConsoleCall` stops at `updated_at`). They exist so two agents cannot claim the same call. Wire them when takeover goes real.
- `call_dispatch_status(dispatch_id, event_id, contact_id, call_attempt_id, status, reason, created_at, updated_at)` — one row per manual dispatch request. Already wired (`SupabaseCallEngineImpl.enqueueOutboundCall` + `fetchTrackedDispatchStatuses`).
- `human_agent_call_legs(id, call_attempt_id, agent_id, request_id, mode, status, vox_sdk_call_id, vox_leg_call_id, device_id, requested_at, connected_at, disconnected_at, failure_code, metadata)` — realtime-published; server creates the `requested` row when `/api/calls/{id}/monitor` is called, the VoxEngine scenario advances it through `dialing → ringing → connected → disconnected|failed|cancelled`. **Not read by the app yet** — this is the row to watch once monitor/takeover wiring starts.

Read-only VIEWS (fetch/poll only — Supabase Realtime does not fire on views):
- `console_campaigns(id, event_id, status: approved|closed, enabled, start_at, close_at, max_contacts)` — billing columns intentionally hidden
- `console_rsvp_results(id, event_id, guest_id, guest_name, attending: boolean, adults, kids, note, created_at)` — note `attending` is a BOOLEAN, not an enum
- `console_campaign_targets(id, event_id, campaign_id, contact_id, status, current_step_index, next_run_at, reached_at, reached_channel, stop_reason, guest_name, phone)` — `phone` is empty unless the agent holds the `view_customer_data` platform permission
- `console_me(user_id, display_name, vox_username, platform_role, platform_rank, permissions)` — the agent's own identity row, and the source of `vox_username` for SDK login
- `console_event_guests(guest_id, event_id, guest_name, dialable, phone, rsvp_status, has_active_campaign, reached_at, callback_scheduled_at, can_start_outreach_call, call_block_reason)` — manual-dial projection. Enable only when `dialable && has_active_campaign && can_start_outreach_call == true`; nullable booleans are fail-closed.

Write ownership (hard rule): the console READS. RSVP outcomes are written by the ElevenLabs client-tools pipeline; campaign state is billing-coupled and changed only via `POST /api/campaigns/{id}/status`; `outreach_state` belongs to the orchestrator. The only direct writes allowed: own `agent_status` row, and `handled_by`/`agent_id` on `console_call_feed` at takeover.

Gate: console access requires membership in `console_agents` **AND** platform staff membership — `is_console_agent()` is `is_staff() AND exists(console_agents…)`, and `console_agents.user_id` is a foreign key to `platform_staff(user_id)` with `ON DELETE CASCADE`. Consequence for the app: an agent removed from staff loses console access instantly and silently. Treat a sudden empty feed plus RLS denials as "access revoked", not as a network fault.

## API contract (the ONLY external HTTP calls; JWT = Supabase session token)

Base `https://beta.kalfa.me`, header `Authorization: Bearer <jwt>`. This list must match `beta/docs/voice-agent/app-integration-reference.md` (the server's own, actively-maintained record of this contract) and `beta/src/lib/validation/agent-console.ts` in meaning — if they disagree, the server side wins (hard rule 7) and both get fixed together. Never invent a path.

- `POST /api/agents/status` `{"status":"ready|not_ready|dnd"}` → `200 {"ok":true,"status":"..."}`. `in_call` is never client-submitted. **Wired.**
- `POST /api/agents/shift` `{"active": true|false}` → `200 {"ok":true,"active":...}` — standing "on shift" intent for auto-connect-on-launch and the off-duty push-wake audience (see "Push wake-up"). **Live server-side since 2026-08-12. Not called by the app yet.**
- `POST /api/events/{eventId}/outreach-call` `{"guest_id":"uuid"}` → `202 {"status":"accepted","dispatch_id":"uuid","event_id":"uuid"}`. A reached contact returns `409 {"code":"already_reached"}` and creates no job. **Wired.**
- `POST /api/agents/sdk-auth` `{"one_time_key":"..."}` → `200 {"hash":"..."}` — server-side Voximplant login hash (§1 above). Username is resolved from the JWT, never sent in the body. `409` means "authorised, but no SDK identity provisioned" — stop, do not retry. **Live server-side; SDK client code written (`VoxSdkAuthClient`), not yet invoked from any call site.**
- `POST /api/calls/{id}/agent-command` — flat body, not nested under `payload`:
  - `{"command":"contextual_update","text":"…"}` → non-interrupting whisper
  - `{"command":"user_message","text":"…"}` → injects a user turn; **interrupts**
  - `{"command":"clear_buffer"}` → one-shot barge-in
  - `{"command":"close_agent"}` → closes the AI leg, call stays up
  - `text` trimmed, non-empty, max 1000. Strict object — an extra field is a 400. `409` when the call is no longer live. Returns `202 {delivered, applied: "pending"|"confirmed"|"rejected", command, request_id}` — `202` is not "done"; for the two text commands `applied` stays `"pending"` forever (ElevenLabs never acks). **Wired.**
- `POST /api/calls/{id}/end` `{}` — ends the whole call (hangs up on the guest), deliberately separate from agent-command so a mistap can't end a live conversation with one enum value. **Wired.**
- `POST /api/calls/{id}/monitor` `{"mode":"monitor"|"takeover"}` → `202 {"attached":true,"leg_id":"…","request_id":"…","mode":"…"}`. Requires `manage_voice`. **Route, auth, and leg-recording are built server-side; returns `503` until `app_settings.monitor_enabled` flips (blocked on the VoxEngine scenario + live verification — see "Telephony integration spec" §4). Not called by the app yet.**
- `POST /api/campaigns/{id}/status` `{"action":"activate"|"pause"}` → `200 {"ok":true,"status":"..."}`. Requires `campaigns.runstate`, not `manage_voice`. Scope is narrow by owner decision: `active→paused` and `paused→active` only; first activation stays on the web. **Wired.**

**Permissions gate the UI, not just the route** — `console_me.permissions` carries `manage_voice` / `campaigns.runstate` / `view_customer_data`; don't render a control the caller's permission set can't back (a 403 that reaches the user is a UI bug, per the server contract's own rule — "never render a control with no backend behind it").

## Build & CI

- Local: create `.env` (see `.env.example`) with real `SUPABASE_URL`/`SUPABASE_ANON_KEY`, or the app builds and runs in full mock mode (fabricated data, no login — see "Known state" item 11).
- `.github/workflows/android-build.yml` writes `.env` from repo secrets `SUPABASE_URL`/`SUPABASE_ANON_KEY` when present (real/configured build); otherwise falls back to `.env.example` with a loud `::warning::` (mock build) — never silently. Unit tests are NOT `continue-on-error` — a real test failure fails the run. Tests and the debug APK always run and are expected to pass on every push; they do not depend on release signing or FCM config.
- **`google-services.json`** (FCM push config, since the 2026-08-14 push-wake-up work) is gitignored — the repo is public and the file names the Firebase project and its API keys, so it is stored as the base64 repo secret `GOOGLE_SERVICES_JSON_BASE64` and decoded to `app/google-services.json` by the "Provide google-services.json" CI step, the same pattern as the release keystore below. `app/build.gradle.kts` applies the `google-services` Gradle plugin **conditionally** on that file's presence: absent → the debug/test build still runs (no FCM, loud `::warning::` + job-summary note); present → normal behavior, including the plugin's own hard failure if the file is malformed. To add the secret: `cat app/google-services.json | base64 -w0 | gh secret set GOOGLE_SERVICES_JSON_BASE64 --repo nm-digitalhub/KALFA-ELEVENLABS`.
- **The release AAB/APK are only built when BOTH the release keystore secrets AND `google-services.json` are present** — checked in one "Check release readiness" step. `app/build.gradle.kts`'s `release` signing config looks for `KEYSTORE_PATH`/`STORE_PASSWORD`/`KEY_PASSWORD` env vars and falls back to generating a fresh `debug.keystore` when they're absent; Play requires the SAME signing key across every release, so a build signed this way could never be uploaded to Play — CI refuses to produce one rather than let it look uploadable. Missing FCM config is refused for the same reason: a release artifact should never ship with silently-broken push. When either is missing, the release steps are **skipped** (not failed) with a `::warning::` and a job-summary explanation — this must never take down unit tests or the debug APK, which have nothing to do with it. Provisioning one real upload keystore and wiring `RELEASE_KEYSTORE_BASE64`/`RELEASE_KEYSTORE_STORE_PASSWORD`/`RELEASE_KEYSTORE_KEY_PASSWORD` as repo secrets is required before any Play distribution, internal testing track included.
