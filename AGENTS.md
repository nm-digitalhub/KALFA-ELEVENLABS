# AGENTS.md — KALFA Agent Console (native Android)

Call-center agent app for kalfa.me (Hebrew RSVP SaaS): agents supervise AI voice-RSVP calls, take inbound calls, run outbound campaigns, and watch a realtime dashboard.

**This app is a separate product from `kalfa.me/beta` (the Next.js web app).** It talks to that server over the HTTP contract in §"API contract" and reads the same Supabase project through PostgREST/Realtime with the agent's own JWT. It does not share code, a repo, or a deploy pipeline with `beta/`. Where a decision genuinely depends on how the server works, this file says so and names the boundary — it does not restate the server's implementation.

## Hard rules

1. **Hebrew-first RTL.** All user-facing strings in Hebrew. `LayoutDirection.Rtl` everywhere; paddings/margins use `start`/`end` only — never `left`/`right`. Phone numbers, digits, times, and dates render LTR inside RTL text.
2. **Design system: Bento Grid.** Keep the established Bento Grid layout language — rounded cards on a clean canvas, flat design, no gradients. Brand: primary `#6C4CF1`, secondary `#6366F1`.
3. **Supabase is the ONLY backend.** supabase-kt (auth-kt, postgrest-kt, realtime-kt) version 3.x with Ktor 3.x. Package is `io.github.jan.supabase.auth` (not gotrue). No Firebase Auth / Firestore / any Firebase dependency — the single exception is `firebase-messaging` (FCM push only). Secrets never in code: `SUPABASE_URL` / `SUPABASE_ANON_KEY` reach BuildConfig via the secrets-gradle-plugin from the git-ignored `.env` file (see `.env.example`).
4. **Telephony lives behind `CallEngine` / `CallSession` / `AgentPresence`.** Do NOT rename or remove these interfaces — every swap happens behind them.
   - **The Voximplant SDK line is v3** (`com.voximplant:android-sdk-bom` + `-core` + `-calls`, version `3.2.0`), NOT the legacy monolithic v2. This app is Compose + coroutines end-to-end, so v3 (modular, coroutine-friendly, actively maintained) is the right line — the earlier "v2 GA, v3 still Beta" call this file used to make is stale; v3 left beta in 2026-07 and this app has been building against it since.
   - **A real v3 login + call-session layer already exists**, under `telephony/vox/`: `VoxClientManager` (connect/one-time-key login, MAU-safe — never logs in speculatively), `VoxSdkAuthClient` (talks to `POST /api/agents/sdk-auth`), `VoxCallSession` (wraps a real `Call`: mute/hold/DTMF/hangup, state mapping), `VoxAudioController` (device selection), plus `telephony/CallForegroundService` (microphone-type FGS) and `telephony/CallAudioPermissions` (RECORD_AUDIO + POST_NOTIFICATIONS, already requested on the live-calls screen).
   - **`startOutboundCall`/`monitorCall`/`takeoverCall` are still not wired into `CallEngine`.** `SupabaseCallEngineImpl.startOutboundCall` / `.monitorCall` / `.takeoverCall` all `throw UnsupportedOperationException` on purpose (`data/SupabaseImplementations.kt:892-906`) — they used to fabricate a `MockCallSession`, which was the worse, dishonest option, and were changed to fail loudly instead. **Update 2026-08-14 — the *inbound-to-human offer* path is now wired, narrowly, outside those three methods:** `ensureLoggedIn` is called from `ConsoleViewModel.setAgentStatus(READY)` (via `telephony/presence/PresenceActions`, shared with the presence notification's shade actions) and `VoxClientManager.onIncomingCall` is assigned in `DependencyContainer` to `VoxIncomingCallCoordinator::handleIncomingCall`, which answers the incoming SDK call, publishes it via new `CallEngine.attachIncomingSession`/`clearAttachedSession` methods, and starts/stops `CallForegroundService` around the leg — see `docs/android-presence-and-call-ux.md` §3. The hand-written `ConsoleConnectionService` stub was deleted rather than built — the AAR supplies `androidx.core.telecom.internal.JetpackConnectionService` and declares `MANAGE_OWN_CALLS` itself.

     `FOREGROUND_SERVICE_PHONE_CALL` is still undeclared, and the stated reason ("it belongs with the `CallsManager.addCall` migration") is **wrong** — see §"Play upload" item B-2. ## Push wake-up — resolved architecture, and a caveat that matters more than the architecture

**The reason this app exists:** the browser PWA only receives calls while a tab is open and its 60s heartbeat keeps flowing — a closed laptop silently drops out of the routing pool (`agent_status.updated_at` ages past the 90s freshness window server-side; see `beta`'s `AGENT_STATUS_FRESHNESS_MS` / `findRoutableAgents`). A foreground service fixes "stays reachable while the app is running." It does **not** fix "gets woken when the app isn't running" — that needs push.

### Decided 2026-08-14: Voximplant delivers the push itself — no backend work in `beta`

Two candidate architectures were considered. Verified against live Voximplant docs (`references.androidsdk3.*`, `guides.sdk.android-push`), quoted verbatim: *"Call push notifications are sent automatically. Call the `callUser` method in the VoxEngine scenario and a push notification is automatically sent to the app."* Corroborated by a platform-emitted `Call.PushSent` event with a `push_results[]` array in session logs — the platform reporting on its own send.

**So: no `firebase-admin`, no new Supabase table, no new API route, no new secret, no backend send path in `beta`.** A self-hosted FCM sender (a `console_agent_push_tokens` table + `POST /api/agents/push-token` + a `src/lib/push/fcm.ts` send path parallel to the existing web-push stack) was fully specified in an earlier pass of this document and then ruled out for exactly this reason — it would have duplicated infrastructure Voximplant already provides on the one path where the platform is the natural owner. Not reproducing the detail here on purpose; if this decision needs re-deriving, start from the Voximplant guide quote above, not from scratch.

**What beta's existing push stack (`src/lib/push/{web-push,types,browser}.ts`, `push_subscriptions` table) still is:** Web Push (VAPID) for the browser PWA only. It was never a candidate for the native path — the table shape (`endpoint`/`p256dh_key`/`auth_key`) is Browser Push API-specific and has no equivalent for a Voximplant-delivered native push. Nothing about it changes; it just isn't part of this story.

### What IS needed — entirely client-side, in this repo

- **One-time ops action, not code:** upload the Firebase service-account JSON to the Voximplant control panel (Applications → `kalfa-rsvp` → Push Certificates → GOOGLE). Without this, `callUser` sends no push regardless of anything the app does.
- **Scenario side, one line:** `require(Modules.PushService);` added to `ConsoleInbound.voxengine.js` — no change to any `callUser` call site. Server/ops work, out of this repo, but trivial compared to the backend spec that was ruled out.
- **App side (the actual work here):**
  - Standard Firebase client registration: `google-services.json`, the Google Services Gradle plugin — this is the sink for the `firebase-messaging` dependency that has sat unused since the project was scaffolded. Note the plugin isn't just missing, it was **deliberately removed**: commit `337823b` stripped it from the AI Studio export precisely because there was no JSON yet ("google-services plugin (no JSON yet)"). Re-adding it is a real, if small, step — not just dropping a file in.
  - A `FirebaseMessagingService` subclass forwarding `onMessageReceived` into `Client.handlePushNotification(map)`.
  - `registerForPushNotifications(PushConfig(token))` called after a successful SDK login.
  - `VICalls.setIncomingCallListener` (already present in `VoxClientManager` — `onIncomingCall`) is what fires once the platform delivers the woken-up incoming call.
  - **Persisted-token silent login** (`loginWithAccessToken`/`refreshToken`), not the one-time-key flow, for the wake path specifically: a push-woken app has no human present to type a password, and Voximplant's own guide discourages storing one. The one-time-key flow in "Telephony integration spec" §1 is still correct for an interactive, foreground login — this is a second, separate login path needed only for the wake case.

### The caveat that matters more than the architecture: push does not fix the 13.8 incident

**Verified directly** (`beta/src/app/api/voximplant/console/route-inbound/route.ts:171,242` and `src/lib/data/console-calls.ts`'s `findRoutableAgentVoxUsernames`): `ConsoleInbound` only rings usernames the SERVER hands it as `ring_order`, and `ring_order` is built from `findRoutableAgentVoxUsernames()` — the SAME `status='ready'` + fresh-heartbeat gate as everywhere else in this document. An agent with a stale heartbeat is excluded from `ring_order` **before `callUser` is ever attempted** — which is exactly what happened on 2026-08-13 (`status='ready'`, heartbeat 661 minutes stale, every call answered "no agent available"). No `callUser` attempt means **no push would ever have been sent**, push infrastructure notwithstanding.

**Push solves the telephony layer** (a `callUser` attempt reaching a backgrounded or killed app). **It does nothing for the routability layer** (an agent already excluded before `callUser` is tried).

**Update, 2026-08-14 — the server half has since been decided and shipped** (`beta` commit `8af24ab`, deployed). The resolution was NOT to loosen the freshness gate. Instead, `POST /api/voximplant/console/route-inbound-retry` — the one-shot RETRY wave the scenario fires after the primary ring is exhausted — now returns two audiences in order: heartbeat-fresh agents first (awake, answer immediately), then agents whose `console_agent_shift` row is active and fresh, **without** the heartbeat requirement. Ringing that second group is precisely what makes Voximplant push their device: no `callUser`, no push.

What that changes for this repo:

- **The primary ring is unchanged.** A stale-heartbeat agent is still excluded from the first pass, exactly as on 2026-08-13. This adds a second chance after the first pass fails; it does not make that incident impossible, and nobody should describe it that way.
- **The server side now needs nothing further.** What remains is entirely in this repo (FCM registration, `FirebaseMessagingService`, silent login), plus the one-time control-panel upload and the one-line `require(Modules.PushService);` in the scenario — both ops, not app code.
- **This app must call `POST /api/agents/shift` for any of it to work.** It currently does not (see the API-contract section). With no `console_agent_shift` row, the retry wave will never include this agent and no push will ever be sent, no matter how correctly the FCM side is wired. Treat wiring `/api/agents/shift` as part of the push-wake work, not an optional extra.
- **The cold-start budget is real and unmeasured.** The retry wave rings with `RING_RETRY_WINDOW_MS` (15s) — tighter than the primary `RING_PER_AGENT_MS` (20s). FCM delivery, connect, silent login, `onIncomingCall` and answer all have to fit inside it. No documented SLA covers this; it needs a live-device timing test before anyone claims the path works.

### Two more things worth knowing before this gets built

- **MAU is not the constraint it was treated as earlier in this document.** Multiple devices logged in under one credential count as ONE MAU, and a push-triggered reconnect + silent login on the SAME credential is another login on that same credential — it does not multiply per wake-up. The underlying discipline ("don't log in speculatively when there's nothing to do yet") is still good practice for the interactive one-time-key path, but MAU exhaustion specifically is not a realistic risk for the push-wake path.
- **Unmeasured timing risk, flag before trusting this in the primary ring:** a cold wake — FCM delivery → SDK connect → silent login → `onIncomingCall` fires → app answers — has to complete inside `RING_PER_AGENT_MS`, **verified as `20000` (20s)** in `beta/voxfiles/scenarios/src/ConsoleInbound.voxengine.js:84`. Voximplant's docs promise the push is sent "without delay" but give no number for end-to-end wake latency on a real device. This needs a live-device timing test — cold app state, real network, real OEM — before push-wake is trusted to answer in the primary ring rather than being scoped to a retry wave. Also account for Doze/OEM battery managers, which can swallow a push the platform's own `Call.PushSent` log reports as delivered — "the platform says it sent it" and "the device received it in time" are different claims.

### 1. Authentication — mostly done, verify against this before changing it

### 4. Live Monitor & Takeover (server-verified topology — do not reinvent)

This section previously described a pattern (`Conference.add(EndpointParameters)` taking an `AgentsClient`) that does not compile against the real typings and was corrected on the server side after a live-docs check. The verified topology, 1:1 from Voximplant's official supervisor guide (`beta/docs/voice-agent/monitor-scenario-topology.md`):

- A `Call` receives only **one** audio stream — a new `sendMediaTo` source replaces the previous one. A leg that must hear two sources (guest + AI) needs a mixer: `VoxEngine.createConference()`, **not** `Conference.add()` (which needs a video-conference rule flag and does not accept an `AgentsClient` at all).
- `monitor` = Supervision mode: `guest.sendMediaTo(conf); agent.sendMediaTo(conf); conf.sendMediaTo(human)` — the human leg only receives.
- `takeover` = full Conference mode: all three legs `sendMediaBetween`/`sendMediaTo` the mixer both ways.
- This is **entirely server/VoxEngine-scenario work** (`RSVPAgent.voxengine.js`), gated behind `app_settings.monitor_enabled` and blocked on live-call verification — not something to implement from the app side. The app's job once the server flag is on: call `POST /api/calls/{id}/monitor` `{mode}`, get back `202 {leg_id, request_id}`, watch `human_agent_call_legs`/Realtime for `dialing → ringing → connected`, and answer the incoming SDK call that arrives via `VoxClientManager.onIncomingCall` — wrapping it in a `VoxCallSession` with `connectedState = MONITORED` or `TAKEN_OVER` (both already exist as domain states, see `CallSession`/`CallState`).
- **Open owner decision, not resolved yet:** whether `takeover` should mean a 3-way conference (agent+human+guest, AI never disconnected) or a full swap (AI closed via the existing `close_agent` command, guest left alone with the human).   - `{"command":"user_message","text":"…"}` → injects a user turn; **interrupts**
  - `{"command":"clear_buffer"}` → one-shot barge-in
  - `{"command":"close_agent"}` → closes the AI leg, call stays up

Returns `202 {delivered, applied: "pending"|"confirmed"|"rejected", command, request_id}` — `202` is not "done"; for the two text commands `applied` stays `"pending"` forever (ElevenLabs never acks). **Wired.**
- `POST /api/calls/{id}/end` `{}` — ends the whole call (hangs up on the guest), deliberately separate from agent-command so a mistap can't end a live conversation with one enum value. **Wired.**

Requires `manage_voice`. **Route, auth, and leg-recording are built server-side; returns `503` until `app_settings.monitor_enabled` flips (blocked on the VoxEngine scenario + live verification — see "Telephony integration spec" §4). #### A-1. The full-screen-intent question — answered

**Registering a self-managed `PhoneAccount` does *not* satisfy Play's criterion.** The criterion is a **Play Console declaration form**, evaluated by review. Two policy pages say so directly:

> "**Submit a declaration form in your Play Console to establish pre-grant eligibility for the full-screen intent permission if targeting Android 14+**" … "Apps that request this permission are **subject to review**, and those that do not meet the above criteria will not be automatically granted this permission."
> — *Permissions and APIs that Access Sensitive Information* (16558241)

> "If you use the `USE_FULL_SCREEN_INTENT` permission, you are required to complete the Play Console declaration starting May 31, 2024… Starting January 22, 2025, for apps targeting Android 14+, only apps that have calling or alarm functionalities will have this permission enabled by default. Otherwise, you must get user permission… **For apps that did not complete the declaration or have not been approved for default enabling**, developers will need to prompt users to grant permission on new installs and gracefully degrade the experience if denied."
> — *Understanding foreground service and full-screen intent requirements* (13392821)

`CallsManager.registerAppWithTelecom` runs on the device, after install. Play's review pipeline never observes it. So it is **not the mechanism** — but it is **not useless either**, and `TelecomRegistration.kt`'s kdoc should not be read as claiming otherwise. The correct model:

- **The declaration is the gate.** Without it the app lands in the "did not complete the declaration" bucket → no default grant → locked-screen ringing dies silently at publication, exactly the failure that file was written to prevent.
- **`MANAGE_OWN_CALLS`, the self-managed `PhoneAccount`, and `CallStyle` are the substantiation** that makes the "receiving phone or video calls" claim survive "subject to review". They are worth having *because* the declaration is reviewed.
- **The declaration is necessary but not sufficient** — "or have not been approved for default enabling". Approval can simply not land.

**Therefore the `RingCapability` degradation path stays, permanently.** `telephony/vox/RingCapability.kt` already checks `NotificationManager.canUseFullScreenIntent()` and offers `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`, which is precisely the "prompt users to grant permission on new installs and gracefully degrade" the policy demands. It is the app's only safety net if approval does not arrive. Do not delete it on the strength of a submitted declaration.

The claim itself is strong and should be made confidently: the app's core function is receiving routed calls, it renders `NotificationCompat.CallStyle.forIncomingCall` with `CATEGORY_CALL` (`IncomingCallNotificationBuilder.kt`), and it registers a self-managed `PhoneAccount`. **Verified: nothing further is needed in the app to make this claim honest.**

**Hard platform constraint, independent of any Play decision: never remove `USE_FULL_SCREEN_INTENT` from the manifest, and never refactor `CallStyle` away. Either one is a crash, not a downgrade.** AOSP `NotificationManagerService` (`refs/heads/main`, read during this audit) rejects a `CallStyle` notification outright:

```java
if (n.isStyle(Notification.CallStyle.class)) {                       // L8741-8750
    boolean hasFullScreenIntent = n.fullScreenIntent != null;
    boolean requestedFullScreenIntent = (n.flags & FLAG_FSI_REQUESTED_BUT_DENIED) != 0;
    if (!n.isFgsOrUij() && !hasFullScreenIntent && !requestedFullScreenIntent
            && !byForegroundService) {
        throw new IllegalArgumentException(r.getKey() + " Not posted."
                + " CallStyle notifications must be for a foreground service or"
                + " user initated job or use a fullScreenIntent.");
    }
}
```

This app posts the incoming-call notification through `NotificationManagerCompat.notify`, not `startForeground`, so `isFgsOrUij()` / `byForegroundService` are both false — the notification survives *only* via the full-screen intent. And when the app-op is off, `makeStickyHun` (L8266-8277) nulls `fullScreenIntent` and substitutes `FLAG_FSI_REQUESTED_BUT_DENIED` **only** `if (mPermissionHelper.hasRequestedPermission(Manifest.permission.USE_FULL_SCREEN_INTENT, pkg, userId))` — i.e. only because the manifest declares it. Drop the declaration and that last branch disappears too: `IllegalArgumentException` on every incoming call on Android 14+ devices where the app-op is off. The manifest line is load-bearing against a crash, which is a stronger reason to keep it than the Play argument. (Found by `notification-owner`; re-read from AOSP here before recording.)

**Known gap a reviewer could ask about.** The `CallStyle` notification is not associated with a foreground service, which `developer.android.com/develop/ui/compose/notifications/call-style` recommends ("Associate CallStyle notifications on API versions 30 or earlier with a foreground service…"). The doc's `setColorized()` fallback is inert here — AOSP `Notification.java` gates `isColorized()` on `USE_COLORIZED_NOTIFICATIONS` or the notification being FGS/UIJ, and this app has neither. Not a policy violation and not an upload blocker; recorded so the answer exists if it is ever raised. > This app is the console for call-center agents who supervise and take over AI-placed RSVP calls. The server treats a device as routable only if its status was refreshed within 90 seconds; the service refreshes every 30 seconds. That text is written against the four criteria Play actually applies, quoted here so the mapping is checkable — a foreground service must "provide a feature that is beneficial to the user and relevant to the core functionality of the app", be "initiated by the user or… user perceptible", "be terminated or stopped by the user", and "run only for as long as necessary to complete the task" (*Device and Network Abuse* → Permissions for Foreground Services, 9888379). ### B. Risks review, or breaks silently after publication

**B-1 — The Firebase API key must gain Play's app-signing SHA-1.** Already documented in §"Build & CI" with the exact `gcloud` command. Repeated here only because it belongs on this checklist: it cannot be done before the first upload (the certificate does not exist yet) and push breaks for every Play-installed build until it is. **Follows the upload; do it the same day.**

**B-2 — `microphone` is the wrong FGS type for a call, and on Android 14+ it throws on the app's core path.** This is a runtime defect, not only a declaration mismatch. Two independent problems, one fix.

*The runtime problem.* `RECORD_AUDIO` is a while-in-use permission, and:

> "If your app has a while-in-use permission, it only has that permission while it's in the foreground. This means if your app is in the background, and it tries to create a foreground service of type camera, location, or microphone, the system sees that your app doesn't currently have the required permissions, and **it throws a `SecurityException`**." … "you must call `Context.startForegroundService()`… while your app has a visible activity, unless the service falls into one of the defined exemptions."
> — *Foreground services: background start restrictions*, `developer.android.com/develop/background-work/services/fgs/restrictions-bg-start` (exact path noted because the obvious guesses 404 — thanks `permission-owner`)

`VoxIncomingCallCoordinator.handleIncomingCall` starts the `microphone`-typed FGS at line 65 — on the **push-woken** path, whose whole purpose (per its own header comment) is a backgrounded or killed app. There is no visible activity there. **A high-priority FCM message is not among the while-in-use exemptions** — it exempts the *background start*, which is a different restriction. The published exemption list is: a system component starts the service; app widgets; **interacting with a notification**; a `PendingIntent` from a different visible app; device-owner DPC; `VoiceInteractionService`; `START_ACTIVITIES_FROM_BACKGROUND`.

Consequence: the *offer* leg (line 65, before any notification exists) is unexempt and throws; the *answer* leg (line 97, reached by tapping the notification action) is exempt under "interacting with a notification". So the failure is precisely "phone in pocket, locked, call routed" — the scenario the app exists for. Note the existing `hasRecordAudioPermission()` guard does **not** protect against this: the permission is granted, it is merely not *currently usable* from the background.

*The declaration problem.* Play's preset use case for `TYPE_MICROPHONE` is "Background Audio Access… voice commands for virtual assistant without saving, voice recording" — which does not describe a VoIP call. `TYPE_PHONE_CALL` is "Calling: Cellular/VoiP/Telecom APIs" (13392821). Declaring `microphone` and then describing a call in A-2 is a mismatch a reviewer can act on.

*The fix, now unblocked.* The prerequisite for `phoneCall` is:

> "At least one of these conditions must be true: App has declared the `MANAGE_OWN_CALLS` permission in its manifest file. **|** App is the default dialer app through the `ROLE_DIALER` role."

`MANAGE_OWN_CALLS` **is** declared as of `66ad7dc` — verified in the built AAB. The prerequisite is the *declared permission*, not `CallsManager.addCall`; the manifest comment saying `FOREGROUND_SERVICE_PHONE_CALL` "belongs with the `addCall` migration" is mistaken on this point. `phoneCall` has no while-in-use prerequisite, so it does not throw from the background.

**Correction, 2026-08-14 — an earlier version of this item got the mechanism wrong, and the wrong version was acted on.** It said: *"`phoneCall` alone — not `phoneCall|microphone`. The system checks the prerequisites of every declared type."* **That is false.** AOSP `ActiveServices` (`refs/heads/main`) treats the manifest attribute purely as a **subset gate** — L2207, *"Check the passed in foreground service type flags is a subset of manifest foreground service type flags"* — and then validates permissions by looping over **the types passed to `startForeground`**, not the manifest union:

```java
int fgsTypes = foregroundServiceType;          // the startForeground() argument
for (int serviceType = Integer.highestOneBit(fgsTypes);
        serviceType != 0;
        serviceType = Integer.highestOneBit(fgsTypes)) {
    fgsTypeResult = validateForegroundServiceType(r, serviceType, …);
    fgsTypes &= ~serviceType;
    if (fgsTypeResult.first != FGS_TYPE_POLICY_CHECK_OK) break;
}
```

So declaring `phoneCall|microphone` in the manifest is **safe and correct** — it is what makes a per-phase design possible. What matters is the argument to `startForeground`.

**The actual rule, and the state as of `82beccc`:**

1. **Manifest:** `android:foregroundServiceType="phoneCall|microphone"` on `CallForegroundService`, plus `FOREGROUND_SERVICE_PHONE_CALL`. **Done in `82beccc`.**
2. **Code — the half that actually fixes the crash. Landed as `ee881bd` in `fgs-owner`'s worktree; unmerged at the time of writing.** `CallForegroundService.startForegroundCompat` previously hardcoded `ServiceInfo.FOREGROUND_SERVICE_TYPE_MICROPHONE`, and that single argument is the only thing validated — so before `ee881bd` the manifest change fixed nothing and the push-woken `SecurityException` was unchanged. The shipped rule:
   - **Background start (the ring/offer, `VoxIncomingCallCoordinator` line 65):** `FOREGROUND_SERVICE_TYPE_PHONE_CALL` **alone**.
   - **After answer, or via a notification interaction (an exempt path):** `PHONE_CALL or MICROPHONE`.
   - **Never both from the background** — the validation loop `break`s on the first failing type.

**`phoneCall` alone is wrong for the answer phase too, and would fail silently.** My original steer said `phoneCall` everywhere; that is also incorrect, for a different reason than the manifest error. `OomAdjuster` grants microphone capability strictly from the **running** FGS type:

```java
capabilityFromFGS |= (fgsType & FOREGROUND_SERVICE_TYPE_MICROPHONE)
        != 0 ? PROCESS_CAPABILITY_FOREGROUND_MICROPHONE : 0;
```

Without the mic bit the process never gets `PROCESS_CAPABILITY_FOREGROUND_MICROPHONE` — the call connects and captures nothing. (The surrounding `CACHED_COMPAT_CHANGE_CAMERA_MICROPHONE_CAPABILITY` branch grants both capabilities unconditionally when the compat change is *off*. **The gating is target-dependent, not universal** — `@EnabledAfter targetSdk Q`. This app targets 36, so the strict branch is the operative one here; anyone lifting this reasoning to another app must re-check its target first, or they will conclude a bug exists where the permissive branch is running.) That is exactly the "connected call with no audio" failure this item's device-verification note warned about — now with a mechanism rather than a suspicion. It is why the type must be **phased** rather than simply switched. Corroborated by `telecom-owner`'s `ForegroundServiceTypePolicy` reading: `phoneCall` has `foregroundOnlyPermission = false`, `microphone` has `= true`, which is the same asymmetry seen from the permission side. (Found by `fgs-owner`; re-read from AOSP here.)

**A different fix shape exists and was considered — phasing is the more robust choice.** `permission-owner` notes the escape hatch in the same background-start doc: an app *"can start foreground services even while your app runs in the background if your app transitions from a user-visible state, such as an activity"*. So if the full-screen intent brought `MainActivity` up **before** the service started, the original single `microphone` call would be legal and the mic would be kept. Real, but weaker: it makes the core call path depend on the full-screen intent having been granted — the exact thing A-1 says can be revoked at publication and may never be approved — so on an FSI-denied device it degrades back to the crash. The phased-type fix holds regardless of the app-op. Worth knowing both exist if this is revisited; do not swap one for the other without re-reading A-1.

**Why promoting to `microphone` on the second `startForeground` is legal — verified, not assumed.** The obvious objection to the phased design is that the answer-phase call hits an *already-running* service whose first start was denied while-in-use, so the denial might be latched onto the `ServiceRecord`. It is not. `ActiveServices` re-evaluates on every subsequent call — *"The second or later time `startForeground()` is called after service is started. **Check for app state again.**"* (L2504-2516, calling `setFgsRestrictionLocked` again) — and the recompute is guarded by `if ((allowWiu == REASON_DENIED) || (allowStart == REASON_DENIED))` (L8305-8318), so only a stored **denial** is retried while a stored **grant** is left alone. **Grants stick, denials retry.** That asymmetry is what makes the promotion work: the background ring's denial does not poison the answer-phase start, which runs with a visible activity (or via a notification interaction) and therefore satisfies while-in-use. (Found by `telecom-owner`; re-read from AOSP here.)

**Ownership and merge order, settled — and the order is a hard dependency, not a preference.** `CallForegroundService.kt` is `fgs-owner`'s exclusively; `telecom-owner` is scoped to the manifest and build files and confirmed they would not touch it. The service passes a type the manifest must already permit, and the subset gate at `ActiveServices` L2207 rejects the reverse — so **the manifest commits must land before the service commit.** Sequence as reported by both owners at the time of writing: `90841dc` → `82beccc` + `12196e2` → `ee881bd` + `d8e921e` → `b743de0`.

*Wrong-order symptom, per `fgs-owner` (their file, their verification — recorded rather than re-derived here):* since `d8e921e` removed the microphone-only fallback, merging the service ahead of the manifest is **not** a crash and **not** a silent success. It is an answered call with **no ongoing notification and no process protection**, plus a self-diagnosing AOSP message in logcat naming the missing manifest type.

> **Do not dismiss a missing ongoing notification as a cosmetic, notification-only defect — the same failure mutes the call as soon as the screen goes off.** A process gets microphone capability from being visible **or** from a microphone-typed FGS: `OomAdjuster.getDefaultCapability` gives `PROCESS_STATE_TOP` → `PROCESS_CAPABILITY_ALL` outright (L3370-3374), while `PROCESS_STATE_FOREGROUND_SERVICE` grants capability only conditionally on the FGS type. Framing owed to `fgs-owner`, who has it as a release gate on their side too.

**B-3 — AEP Telecom conformance is partial.** The Telecom API requirement asks VoIP apps to "register all incoming and outgoing VoIP calls with the Telecom framework using the `CallsManager#addCall` API", to let Telecom own audio focus and routing rather than using audio/Bluetooth APIs directly, and to use "the `callStyle` API to display call-style notifications". `CallStyle` ✅ (`IncomingCallNotificationBuilder`); `PhoneAccount` registration ✅ (`TelecomRegistration`); **`addCall` ❌**, and `VoxAudioController` drives audio directly. **This is an Apps Experience Program guideline, NOT the Play policy that revokes the full-screen-intent app-op — do not conflate them.** They have different teeth: failing AEP costs a quality-programme badge, failing A-1's declaration costs locked-screen ringing. AEP blocks nothing at upload.

Worth being precise about what `66ad7dc` changed here, because its commit message is misleading on the point: the app was already a VoIP calling app and so already fell under this guideline, so registering a `PhoneAccount` added **no new obligation**. What it did do is move the app into the exact shape AEP names as non-compliant — a registered self-managed account with no `addCall` behind it. That is an argument for finishing `addCall`, not for reverting the registration (which is load-bearing for B-2). It is also the reason B-2's device verification should end at `addCall` rather than stopping at a foreground-service type change.

**B-4 — Data safety must be answered honestly, and one input is unresolved.** What this app transmits off-device, per §"API contract" and §"Data model": the agent's own identity and role (`console_me` → user ID, display name, `vox_username`, permissions), agent status/shift state, and call/campaign/RSVP records — including, for agents holding `view_customer_data`, guest names and phone numbers. Those are **collected** ("Collection means transmitting data off a user's device") and go to `beta.kalfa.me` and Supabase as **service providers**, which per the same page is *not* "sharing" ("data transferred to a service provider doesn't count as sharing"). Disclose under personal identifiers / app activity, and — because guest phone numbers and names reach permitted agents — the corresponding contact-data types.

*The unresolved input, which the owner must settle before answering the audio question:* whether the **human-agent call leg is retained as an audio recording**. It flips the answer between two legitimate outcomes. Live two-way call audio that is only relayed plausibly falls under the ephemeral exemption — data "stored in memory and retained for no longer than necessary to service the specific request in real-time" — and would then not be declared as collected. A retained recording is not ephemeral and **must** be declared as "Voice or sound recordings". Evidence gathered here is suggestive but not conclusive: this app contains no recording code path, and `beta`'s `/api/calls/{id}/monitor` route contains no audio-recording call (its only "record" is `human_agent_call_legs` row-keeping, which is what AGENTS.md's phrase "leg-recording" refers to — database rows, not audio). **Confirm on the Voximplant side whether the agent leg is recorded, then answer.** Do not guess: an incorrect Data safety declaration is a violation in either direction.

  That is a **runtime** question — does this package have a self-managed call *in progress right now* — not a configuration question. Telecom only knows about a call once the app calls `CallsManager.addCall`, and this app never does (see Hard rule 4 and the Telecom phase row). The three documented conditions are necessary but not sufficient; **`addCall` is the missing fourth.** So today, with `POST_NOTIFICATIONS` denied, the incoming-call notification is dropped like any other. ### D. Open question — unresolved, and it undercuts the safety net if true

**Does a full-screen intent require the channel's importance to be `IMPORTANCE_HIGH`, or merely not `IMPORTANCE_NONE`?** `RingCapabilityChecker.channelAlerting` tests only `importance != IMPORTANCE_NONE`. If the platform actually requires `IMPORTANCE_HIGH` for the FSI to launch, that check is too lenient and `canRingOnLockedScreen` can report a device as able to ring on a locked screen when it cannot — a false green light in exactly the degradation path A-1 pins as the app's only safety net.

Not resolved here, and stated as unknown rather than guessed. `permission-owner` tried three sources including the AOSP SystemUI interruption provider; the decision delegates to a `FullScreenIntentDecisionProvider` neither of us reached. Partial mitigation on the current code: `IncomingCallNotificationBuilder.ensureChannel` creates the channel at `IMPORTANCE_HIGH`, so the gap only opens if a **user** later lowers the importance to something between `NONE` and `HIGH` — possible from system settings, not the default state. **Worth closing on a physical device before relying on `canRingOnLockedScreen` for anything user-facing;** do not "fix" `channelAlerting` to demand `IMPORTANCE_HIGH` on speculation, as that would report false negatives instead.
